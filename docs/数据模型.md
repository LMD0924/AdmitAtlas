# 数据模型与字段字典

> **P1 落地口径**：实际建表由 Flyway 在应用启动时自动执行，脚本位于 `back-end-spring-cloud/launcher/src/main/resources/db/migration/`：`V1__schema.sql`（H2 / MySQL 通用 DDL，不使用 `ENGINE` / 分区 / `COMMENT` / `JSON` 列，JSON 内容以 `VARCHAR` 保存）、`V2__seed_demo.sql`（演示数据，全部为合成值）与 `V3__auth_roles_audit.sql`（双身份账号字段、审计日志、数据版本登记、内置账号）。[`back-end-spring-cloud/sql/V1__init.sql`](../back-end-spring-cloud/sql/V1__init.sql) 仅为 MySQL 分区优化**参考脚本**，不参与启动、不由 docker-compose 挂载。下表描述的是逻辑模型，字段命名在 `V1__schema.sql` 中已按 H2 `DATABASE_TO_LOWER=TRUE` 统一为小写。

## 建模原则

1. **位次优先**：`fact_admission_score.min_rank` 是唯一可跨年比较的字段；`min_score` 仅用于展示。
2. **一省一年一版本**：所有事实表带 `province_code`、`exam_year`、`data_version`，支持重算历史方案与回滚。
3. **留证与审核**：采集记录必须带 `source_url` 与 `audit_status`，审核通过后才允许发布。
4. **单科分不入录取事实表**：单科成绩用于同分排序、专业单科门槛，建模在 `rule_policy` 与 `student_score`。

## 索引与量级

- 主查询索引：`idx_query (province_code, exam_year, category, batch, min_rank)`，覆盖「位次区间检索候选院校」这一核心查询。P1 的 `AdmitAtlasRepository.candidateScores(...)` 把 `min_rank BETWEEN ? AND ?` 下推到 SQL 并带 `audit_status = 1`、`data_version = ?`，不在应用层做全量过滤。
- 院校维度索引：`idx_school (school_code, exam_year)`。
- `fact_admission_score` 按 `exam_year` 做 RANGE 分区 —— 这是 **MySQL 生产参考**；H2 / 通用 DDL 不含分区语法。
- 估算：31 省 × 3~5 年 × ~3000 院校 × 20~40 条 = 约 500 万~1000 万行。**MySQL 单库 + 分区足够，不需要分库分表**。
- 缓存：一分一段表、批次线、省份规则全量进 Redis；候选池按 `(省, 年, 科类, 位次区间)` 预计算 —— **P2 目标**，P1 未接 Redis。
- 双身份相关表：`student_profile` 由 V3 补 `display_name` / `account_status` / `token_version` / `last_login_at`；`audit_log` 记录管理端写操作（操作人、动作、目标类型与 ID、前后值摘要、时间）；`data_version_registry` 记录版本状态、覆盖范围、是否演示数据、激活人与时间。密码哈希格式为 `pbkdf2$<iterations>$<salt-b64url>$<derived-b64url>`，绝不出现在任何 API 响应中。
- 数据隔离：`student_score` / `match_task` / `suggestion_plan` 的 `user_id` 取自 `AuthContext`；`plan` 详情与导出会校验归属，非本人且非管理员返回 403。

- P1 演示数据规模：5 个省份维度、6 套规则、14 所虚构院校、10 个专业、6 个选科要求、2023–2026 一分一段（1604 行）、120 条投档记录、2026 招生计划；`demoData = true` 时全站标注「演示数据（合成值）」。
